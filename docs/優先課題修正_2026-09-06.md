push前に本番の稼働状態と移行履歴を再確認した。`ACTIVE_HEALTHY`、適用済みmigrationは従来の6件で、今回の1件は本番未適用である。原本確保・DB全件退避と復元検証は本番切替前の残件であり、Gitへのpushだけで完了扱いにしない。

Supabase `shonan_dx` は再開後に `ACTIVE_HEALTHY`。管理API経由でSQLを実行し、既存の見積1件・請求書1件を読み取れた。業務レコードは変更していない。認証済みブラウザからの本番CRUD確認や、停止原因・再発防止の確定までは含まない。

## 実装内容

| 調査項目 | 第一段階で修正した内容 | 残る点 |
| --- | --- | --- |
| F-01 発行後に内容が変わる | 新規請求書に発行者・組織名・登録番号・宛先・住所・案件・備考・明細・税率・税額・総額をDB側で固定保存。帳票は固定内容のみを使用 | 既存原本の照合、見積提出版の保存、訂正版・PDFファイル保存 |
| F-02 計算不一致 | 明細金額を円単位で四捨五入→小計→課税小計から税額を一度四捨五入。画面・保存・帳票で統一。直接APIからの金額不整合もDBで拒否 | 混在税率、内税、値引き等 |
| F-03 削除・状態の矛盾 | 請求書の更新/削除、請求書化済み見積の内容変更/削除、明細の追加/変更/削除をDBで拒否。請求状態の手動変更を制限 | 取消・訂正・返還の正式ワークフロー |
| F-04 発行者・権限 | 固定会社名を廃止。実際の会社・組織を使用。担当者の見積削除・請求書化をUI/RLS/RPCで拒否 | 顧客/品目編集UIと担当者権限の整合、監査の完全性、招待・承認 |
| F-05 採番 | 4桁以降を保持。請求番号を削除に依存しない非公開カウンタで管理。再試行で同一見積の二重発行を防止 | 見積年の切替UI、年跨ぎ運用 |
| F-06 復元の危険 | 破壊的な旧JSON復元をUI/DBで停止。JSON出力が全件バックアップではない旨を表示 | 全件退避、検証済み復元、取得のページ分割 |

数量0.5も入力・保存できる。単価は整数、数量は小数2桁以内、税率は0〜100%の範囲を今回の計算対象とする。単価101円×数量1.4・税率10%は、小計141円・税14円・総額155円で一致する。

保存済み見積の税率は保持し、新規見積だけに保存済みの初期税率を使う。保存直前にDB側設定が変わった場合は、表示合計と保存合計を比較してRPC全体を取り消し、異なる金額の保存を防ぐ。

## 過去データの扱いと注意

- migrationは既存の請求額や明細を一括再計算しない。
- 既存請求書の発行当時の税率・発行者・宛先は推測しない。固定内容がない請求書は「要原本確認」とし、現在の値での再印刷を止める。保存済みの請求額は確認できる。
- 税率未記録の既存見積は、請求書化前に明細・税率・合計を確認して保存する。既に請求書化されている見積は編集しない。
- 発行済み書類の訂正機能はまだない。削除して作り直す運用は不可。訂正版の関連付けを次段階で実装する。
- JSON復元は請求書の有無にかかわらず一時停止する。既存の復元処理は全削除・ID再生成を伴い、原本を保証できないためである。旧localStorage自体は削除しない。
- `supabase/schema.sql` は参照用の既存資料。新しいDB定義の正本は `supabase/migrations/` にある。

## 検証

- `npx tsc -b`: 成功。
- `npm run lint`: 成功。
- `npm run build`: 成功。日本語を含む新しい画面もビルドを通した。
- `npm test`: 21件成功（DBテスト群の親1件を含む）。
- GitHub Actionsにlintと回帰テストを追加。これらの失敗時にはPagesへ配信しない。

DB検証は、本番から分離したメモリ上のPGliteで行う。既存6件のmigration→旧形式の見積/請求書作成→今回のmigration→RLS/RPC/トリガーの実行という順序で検証した。Supabase AuthのユーザーID取得部分だけをテスト用に用意しており、Supabase全サービスのE2E試験ではない。Docker/psqlがない環境でも `npm test` で再現できる。

主なテストは、税率・マスタ変更後の帳票不変、旧データ保持、0.5/1.4数量、税額の一括丸め、画面合計の食い違い時のロールバック、直接APIでの金額変更拒否、999→1000、二重発行防止、担当者/別組織/未認証の拒否、発行後の明細変更拒否、破壊的復元の拒否。対話メモは請求書化後も追加できる。

PGliteは1接続で動くため、複数接続による同時実行・デッドロック試験は未実施。実際のSupabase環境で追加検証する。ロックとトランザクションの設計だけで並行実行の検証済みとはしない。

Supabase Security Advisorは再開後の現行本番スキーマに対して確認し、漏えいパスワード保護が無効という警告1件を検出した。今回追加したmigrationの本番Advisor結果ではない。Googleログイン中心の現行認証設定は変更していない。[警告の説明](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)

`npm audit`では既存のVite等の依存関係に6件（high 5件、moderate 1件）の警告がある。今回追加したPGliteへの警告はない。無関係なメジャー更新をこのDB変更へ混ぜず、ビルド基盤・依存関係の更新を別の優先課題として残している。

## 本番反映の手順・中止条件

新migration: [20260905162914_protect_issued_invoices.sql](../supabase/migrations/20260905162914_protect_issued_invoices.sql)

1. 管理者と切替時間を決め、旧画面からの入力・発行を止める。既存請求書1件の送付済みPDF等を確保し、原本確認後の扱いを決める。
2. DB全件のバックアップと復元可能性を確認する。現在の画面JSONだけを唯一の退避先にしない。
3. migration履歴・実スキーマの差分を確認する。履歴が想定の6件と異なる、データが増えている、参照整合性が崩れている場合は適用を止めて確認する。
4. migrationをトランザクションで適用し、既存レコードの件数・金額が変わっていないことを確認する。
5. 本番のSecurity/Performance Advisor、担当者/管理者/別組織の許可・拒否、保存・再読込・発行の受入試験を行う。
6. この変更のフロントエンドを配信し、原本未確認の表示と新規請求書の固定内容を確認してから入力を再開する。

フロントだけを先に配信すると、新しい列・RPCがないDBでは読み込み/保存に失敗する。migrationだけを適用して旧画面を使い続けるのも、古い帳票表示が残るので不可。切替中は発行を停止する。

ロールバック時も新しい固定内容やカウンタを削除しない。旧UIへ戻すだけでは再計算表示の問題が戻るため、障害時は発行を止めたうえで前進修正か検証済みDB復元を選ぶ。保護トリガーを外して請求書を削除する回避策は使わない。
