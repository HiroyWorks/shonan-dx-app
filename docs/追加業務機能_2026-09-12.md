# 追加業務機能・導入と復旧手順

更新日: 2026-09-12

## 到達点

依頼された5領域の機能を `codex/protect-issued-invoices` の作業ツリーに追加した。**実装・ローカル検証と、本番反映・実データの照合は別の完了条件**とする。この作業では本番DBへのDDL/DML、Edge Function公開、実メール送信、Git pushは実行していない。

| 領域 | 今回の実装 | 運用前に残る確認 |
| --- | --- | --- |
| 全件バックアップ・復元 | 組織単位の全件・全履歴・採番カウンタ・PDF本体、件数/金額/ハッシュ検証、隔離DBへの実復元・全行比較、空の復旧先限定の復元CLI | 本番データの退避、復旧専用Supabase環境での接続・Auth/Storage受入確認 |

| 下書き・改訂・取消訂正 | 自分用DB下書きと版競合拒否、確定見積の変更履歴、別見積への複製、理由付き取消、同じ顧客の新見積から訂正発行 | 実帳票と訂正運用の受入確認。税務上の返還書類等の個別要件は別途確認 |

## データ設計・保護方針

- 既存の請求書`invoices.snapshot`と金額を再生成しない。既存の未記録の期限はNULL、振込先は空欄のまま残す。
- 支払条件は新規発行時に`invoices`へ固定する。既存原本は別テーブルのPDF/照合情報を追加するだけで、当時の明細を現在値から推測しない。
- 入金は`invoice_payments`へ追記し、訂正は元入金を参照する負の取消行とする。元行を更新・削除しない。過入金・二重取消・取消後の入金を拒否する。入金取消は帳簿上の記録であり、銀行の返金処理ではない。
- 請求取消は`invoice_cancellations`へ追記する。訂正発行では別の未請求見積を利用し、元請求の取消と訂正請求の発行を原子的に行う。入金残高がある場合は先に入金取消が必要。
- 見積履歴は保存トランザクションの最終状態を保存する。導入前の見積には「導入時点の基準版」を1件だけ記録し、過去の改訂履歴を捏造しない。削除した未請求見積の履歴も保持する。
- 保存・新規発行・訂正発行では画面の金額と版番号を照合し、他ユーザーの変更を見落としたまま確定しない。新規見積入力のIDを再試行で維持する。
- 下書きは手動保存。本人の画面だけで参照・更新できるが、組織管理者の全件バックアップには含まれる。
- `invoice-originals`は非公開、1ファイル最大10MB、PDFのみ。ユーザー向けの上書き/削除policyは設けない。既存の別Storage policyが対象バケットにも適用されないか導入時に確認する。
- PDF登録は管理者が目視照合し、番号・金額を再入力して確定する。PDF本文のOCRによる自動照合や電子署名ではない。ハッシュはファイル同一性検査であり、内容の正しさや税法適合を証明するものではない。
- 招待は確認済みの`auth.users.email`で照合する。編集可能なプロフィールメールや`user_metadata`を認可の根拠にしない。申請更新・所属追加は専用RPCに限定する。唯一の管理者の交代は今回の一般UIには含めない。
- 追加テーブルはRLS有効、明示的GRANT、組織単位の参照制限。台帳・原本・送付履歴の直接書込は一般ユーザーに許可しない。必要なSECURITY DEFINER関数は`app_private`に置き、認証・役割・検索パス・実行権限を限定する。

## 検証

- `npx tsc -b`、`npm run lint`、`npm run build`、`npm run check:edge`。
- 自動テスト40件成功。追加テーブルのRLS・匿名権限・SECURITY DEFINERの配置/検索パス・FK索引もローカルカタログで確認。
- PGliteで実際のmigrationを適用し、RLS、権限、改訂、部分入金、二重登録拒否、取消・訂正、招待の偽装拒否を検証。
- 1105件を超える履歴、下書き、原本、採番カウンタを含むバックアップを別の隔離DBへ復元。全行比較とFK整合性を確認し、原本保護トリガーの再有効化も確認。
- 不足PDF、変更されたPDF、件数不一致、金額不一致、参照切れ、既存データへの上書き復元を拒否するテスト。
- メール送信は通信モックで、認証・管理者権限・宛先・原本PDFハッシュ・二重送信防止・結果不明時の送信停止を検証。**実メールは送っていない**。
- ブラウザで架空データの請求管理画面を表示し、日本語・原本照合欄・未回収60000円に対する60001円の入力拒否を確認。実ログインや本番業務の受入試験ではない。
- Vite 4がtsconfig参照先のJSX設定を読まず、分割コンポーネントで実行時エラーになることを画面検証で発見したため、`vite.config.ts`で自動JSX変換を明示した。

PGliteではSupabase Auth/Storageの最小スキーマを用意してSQLを検証する。Google OAuth、実Supabase Storage API、実メールサービス、Supabase上の権限/ネットワーク差異は別途受入検証が必要。

## 本番適用順序（未実施）

1. 利用者の書込停止時間を決める。既存本番のDB全件・Auth・Storageを、提供元のバックアップまたは管理者用dumpで退避する。新しいv2出力RPCは旧本番schemaにはまだ存在しないので、切替前の退避を新UIだけに依存しない。
2. 退避したデータを隔離した復旧環境へ戻し、原本件数・金額・AuthユーザーID・Storageファイルを確認する。既存送付PDFを確保する。
3. 現在の適用履歴を再確認し、未適用の以下3件を順番に適用する。既存migrationの書き換えや`schema.sql`の再投入は禁止。
   - `20260905162914_protect_issued_invoices.sql`
   - `20260912030230_complete_document_workflows.sql`
   - `20260912030648_document_archive_and_backup.sql`
4. 追加テーブルのRLS/GRANT、非公開バケット、Storageの既存policy、DBセキュリティ/パフォーマンスアドバイザーを確認する。
5. `send-invoice`を配信し、下記のサーバー側secretを設定する。フロントエンドの`VITE_*`やGitには秘密鍵を置かない。
6. フロントエンドを配信する。`main`へのpushはGitHub Pagesを自動更新するため、DBより先にmerge/pushしない。
7. 管理者・担当者・別組織・招待ユーザー、見積作成→発行→PDF保管→入金→訂正→全件バックアップの受入確認を行う。メールは所有者が指定したテスト宛先で実施する。
8. 本番v2バックアップを取得し、`backup:verify`で復元検証した後に書込を再開する。

### メール設定

サーバー環境変数：

| 変数 | 内容 |
| --- | --- |
| `RESEND_API_KEY` | 送信ドメインに対する最小権限のAPIキー |
| `INVOICE_EMAIL_FROM` | 検証済みドメインの送信元 |
| `APP_ORIGIN` | 許可するフロントエンドorigin（末尾スラッシュなし） |
| `SUPABASE_URL` / `SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY` | Edge Functionsの標準環境変数。service keyはサーバーだけで利用 |

CLIの`functions deploy`と`secrets set`は実行時に`--help`で確認し、対象project refを明示する。`supabase/functions/.env`はGit対象外。秘密情報はチャットに貼らず、安全なsecret設定経路を使う。

送付履歴は「送信待ち→送信処理中→受付済み/失敗/結果不明」。結果不明時は自動再送せず、Resend管理画面で結果を確認して根拠を記録する。送信処理中は5分間手動確定できない。送信待ち・処理中・結果不明の履歴がある請求書は取消不可。受付済みは配信完了/開封ではない。組織あたり1時間60件の送付登録上限を設ける。

## バックアップ復旧

### 読取専用の復元検証

```bash
npm ci
npm run backup:verify -- backups/estimate-management-full.json
```

このコマンドは本番に接続しない。v2の件数/金額/ハッシュを検査してメモリ内DBに全件を挿入し、全行比較・FK・入金/取消の参照を検証する。認証ユーザーはIDだけをテスト用に再現する。PDFの視覚的内容を確認するものではない。

### 空の復旧用Supabaseへ復元

前提：同一バージョンのmigration適用済み、アプリテーブル全件空、元のAuthユーザーIDが存在、非公開バケット設定済み、公開前で書込・メール送信を停止中。

安全な環境変数で`BACKUP_DATABASE_URL`、`BACKUP_SUPABASE_URL`、`BACKUP_SERVICE_ROLE_KEY`を指定する。直接接続またはSupavisorのDB接続先とStorageのproject refが一致する必要がある。TLSの証明書検証は有効のままにする。

```bash
npm run backup:restore -- backups/estimate-management-full.json --confirm-empty-recovery <組織UUID>
```

復元前に隔離DB検証を実行する。復旧先の全アプリテーブルをロックして空であることを再確認し、ID・発行原本・台帳・版履歴を保存したまま挿入する。一般ユーザー向けRPCから保護トリガーを無効化する機能は設けていない。管理者の復旧トランザクション中だけUSERトリガーを無効化し、FKを有効のまま全行比較を行い、保護を再有効化してcommitする。

PDFはStorage APIで`upsert:false`として復旧し、再ダウンロードしてハッシュ照合する。StorageアップロードとDBは分散トランザクションではない。失敗時はDBをrollbackし、アップロード済みPDFは消さずに残す。再試行は同一ハッシュなら再利用し、異なるファイルを上書きしない。復旧途中ファイルの整理は別途確認して行う。

復元対象は1組織分。既存の別組織があるDBへのマージ、異なるAuth IDへの自動付替え、古いJSON形式の自動変換は行わない。環境全体の復旧にはSupabase提供元のDB/Authバックアップも併用する。

運営管理者の`platform_admins`、Auth/OAuth、メールサービスのsecretなど環境共通の構成は、この組織単位バックアップでは復元しない。環境全体の管理者用バックアップから別途復旧・確認する。チェックサムは改変検知用で署名ではないため、バックアップ本体と検証値を信頼できる保管先に保存する。

## 残る運用課題・範囲外

- 本番データの全件退避・復元、本番migration/Storage/Edge Function適用、実メール送付、Google認証を含む本番E2Eは未実施。
- 原本PDFがない既存請求書は未確認のまま保持する。「原本がないため推測した明細」を確認済みとして登録しない。
- PDFの自動生成・自動保管は今回含まない。既存の印刷/PDF保存から、管理者が原本を照合してアップロードする。
- 原本PDFの差替えUIは意図的に提供しない。登録誤りは運用管理者が原本・理由・監査を確認する個別復旧案件とする。
- メール到達/開封Webhook、督促自動送信、銀行連携、入金の複数請求書一括消込、過入金預り金、返還インボイス、混在税率は未実装。
- 依存関係の監査で既存の7件（高5・中2）が残る。今回の追加機能完了と、アプリ全体のセキュリティ課題解消は同義ではない。
